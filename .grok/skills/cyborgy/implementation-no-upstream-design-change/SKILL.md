# 実装者は設計を変更しない

渡された設計に従って実装する。**上位の設計変更を自分の判断で行ってはいけない。**

## 手を止めるべきとき

次のいずれかに該当したら、その場で作業を止める。

- 渡された設計のとおりに実装すると動かない
- 設計が前提としている構造が、実際のコードに存在しない
- 設計どおりにすると、既存の振る舞いが変わる
- 設計に書かれていない判断をしないと先に進めない
- 設計が参照している行番号やシンボルが、現在のコードと一致しない
- **設計どおりにすると、層を越える参照が必要になる**（次節）

## そのときに取る行動

**元の設計者にメッセージを送り、設計の変更を依頼する。**

送る内容には次を含める。

- どこで止まったか（ファイルと行、対象の関数名）
- 設計のどの記述が、実際のコードのどの事実と食い違うか
- 自分が確認した事実。**推測と区別して書く**
- 設計を変えずに進める案があるなら、それも添える。ただし**採否は設計者が決める**

元の設計者に到達できない場合は、**設計ができる水準のモデルに依頼する。**
自分より上位の判断を、自分で代行しない。

## 層を越える参照を勝手に作らない

コードは、**何を知ってよいか**で `platform` / `external` / `domain` /
`application` の 4 層に分かれている。`external` と `domain` は兄弟で、
互いを参照しない。層の定義と判定方法はリポジトリのスキルにある。

実装中に層を越える import が必要になったら、**それは設計の問題である。**
止めて依頼する。次のいずれもしてはいけない。

- 層判定の許容表（`ALLOWED` など）を広げてテストを通す
- モジュールの層登録を、通るところに変える
- 遅延 import や文字列経由の参照で判定をすり抜ける

テストが落ちたなら、import が間違っているか、層の選択が間違っている。
どちらかは設計者が決める。

## 既存コードを変更するとき

既存コードには層の規則を満たしていない箇所がある。**一括で直さない。**

> **自分が変更するコードについては、その変更の中で規則を満たす状態にする。**

触っていない箇所を直しにいかない。触った箇所を不適合のまま残さない。

適合させるための影響範囲が、今回の変更の目的に対して広すぎる場合は、
**範囲と理由をユーザーに示して判断を仰ぐ。** 示すのは次の 3 点。

1. 適合させるにはどのモジュールをどの層へ動かす必要があるか
2. それによって変わる呼び出し側の数
3. 今回の変更本来の目的と、その規模の対比

**判断を仰がずに、満たさないまま進めない。** 黙って進めると、不適合が
「影響範囲が広いから残したもの」なのか「気づかなかったもの」なのか、区別がつかなくなる。

**層を移動させる変更と、振る舞いを変える変更を、同じ変更に混ぜない。**
混ぜると、壊れたときにどちらが原因か分からなくなる。

## してはいけないこと

- 設計を「解釈で補って」進める
- 動くほうへ寄せて実装し、後から報告する
- 設計に書かれていない構造を追加する
- 設計に書かれた制約を、都合が悪いので外す
- 「明らかにこうすべき」と考えて設計と違う実装をする

設計に不備があったとしても、それを直すのは設計者の仕事である。実装者が直してしまうと、**設計者はその判断を検証できない。** 正しい変更であっても、検証されない変更は以降の前提を壊す。

## 場合によっては報告だけして進む

設計に「直したくなるが直してはいけないもの」が明示されていることがある。その場合は手を止めず、**直さずに報告して先へ進む。**

バグ、重複、デッドコード、不適切な名前などを見つけても同じである。場所と内容を報告するだけにし、今回の作業に混ぜない。

## 実装者が自分で解決してよいもの

設計判断を伴わない細部だけ。

- コンパイルエラー・型エラー
- ライブラリのバージョン不整合、API シグネチャの差異
- import、リンタ、フォーマッタ
- 環境固有の差異（パス、OS、シェル）

**判断に迷ったら、それは設計判断である。** 止めて依頼する。
