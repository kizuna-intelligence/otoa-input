# ライブラリ化は「同じ問題」にだけ行う

## 先に層を決める

共通化の前に、そのコードが**何を知ってよいか**を決める。
リポジトリに層の定義があるなら、それに従う（例: `platform` / `external` /
`domain` / `application`）。

**層が違うものは共通化しない。** 層が違うということは、知ってよい範囲が
違うということであり、変更の理由が違うということである。
今同じコードに見えても、一方の事情でもう一方が引きずられる。

## ライブラリにしてよい条件

次の 3 つが**すべて**成り立つときだけ。

1. **解いている問題が同じ**
2. **問題の構造が同じ** — 入力、不変条件、失敗の種類、境界条件、呼ばれる文脈
3. **同じ解を提供できる** — 呼び出し側ごとの例外的な分岐を足さずに済む

## これを理由に共通化しない

- 表面的な振る舞いが似ている
- コードの見た目が似ている
- 行数が減る
- 「いずれ同じになりそう」

似ているだけのものを 1 つにすると、片方の要求が変わるたびに引数と分岐が増える。**分岐の増えた共通化は、元の重複より高くつく。** 重複は後から統合できるが、誤った共通化は分離が難しい。

**判定に迷ったら共通化しない。**

## 名前が判定になる

ライブラリには**解いている問題の名前**を付ける。

`util` / `common` / `helpers` / `misc` / `shared` に置きたくなったら、それは
**「同じ問題」を特定できていない証拠**である。名前を付けられないものは、まだ
ライブラリにする段階にない。重複のまま置いて、同じ問題だと判るまで待つ。

層名が「何を知ってよいか」を、モジュール名が「何を解いているか」を表す。
両方が必要である。

## 既存のライブラリは探してから書く

実装を始める前に、同じ問題を解くものが既にあるか探す。
探す範囲はまず**同じ層**である。

ただし**見つけたら使う、ではない。** 使う前に確かめる。

1. そのライブラリが解いている問題は、自分の問題と同じか
2. **既存の呼び出し側がどう使っているかを読む** — 名前とシグネチャだけで判断しない
3. 自分の用途のために引数や分岐を足す必要があるか

**足す必要があるなら、それは同じ問題ではない。** 使わずに別で書き、
なぜ違うのかを記録する。

同じ問題なのに使わず再実装すると、**実装が分岐して片方だけ直る**。
これは重複ではなく、時間とともに振る舞いがずれていくバグである。

使いたいライブラリが**上位の層にある**場合は、使えない。
層を越えて参照するのではなく、必要な値を引数で受け取るか、
そのライブラリの層が間違っていないかを疑う。

## 同じ問題なのに振る舞いが違うものを見つけたとき

同じ問題を解く実装が複数あり、**振る舞いが食い違っている**場合、それは
統合の機会であると同時にバグである。

どちらが正しいかを自分で決めて片寄せにしない。差分を列挙して報告する。
統合とバグ修正を同じ変更に混ぜない。混ぜると、どちらが原因で壊れたか分からなくなる。

## ライブラリにしないという判断も記録する

似ているが別だと判断したものは、**なぜ別なのかを短く残す。**
次に見た人が同じ検討をやり直さないようにするためであり、
将来本当に同じ問題になったときに気づけるようにするためである。
