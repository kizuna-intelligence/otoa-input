# 長い処理は通知が返る形で起動し、通知を受けて再開する

数十秒以上かかる処理を起動するときは、**完了が自分に通知される形で起動する**。
通知が返らない起動をすると、結果を見ないままターンが終わる。そのあとに結果を
語れば、それは見ていないことを語ることになる。

## 対象

- ビルド、デプロイ、コンテナの起動と読み込み、学習、長いテスト
- コマンド経由のエージェント起動（`codex exec`、`cursor-agent`、`claude -p` など）
- リモートのジョブ、CI、キューの待ち

一瞬で終わるコマンドは対象外。

## 起動のしかた

**Bash を `run_in_background: true` で起動する。** プロセスが終了した時点で
再び呼ばれ、出力ファイルの場所が渡される。これが既定。

    Bash({ command: "...", run_in_background: true })

**流れてくるものを見張るときは Monitor を使う。** 一行ごとに通知が来る。
失敗の signature も grep に入れる。成功だけを見張ると、落ちたときに沈黙し、
沈黙は「まだ動いている」と見分けがつかない。

    tail -f run.log | grep -E --line-buffered "done|Traceback|Error|FAILED|Killed"

**やってはいけない起動**

- `cmd &` で切り離す。終了を知る手段が残らない。
- 前面で長時間ブロックする。タイムアウトで打ち切られ、結果が失われる。
- `sleep N` を繋いで待つ。待っている間は何も進まず、外れれば取りこぼす。

条件が満たされるまで待ちたいなら、待ち自体を背景に置く。

    Bash({ command: "until <条件>; do sleep 5; done", run_in_background: true })

## 通知が来たら

**出力ファイルを読み、作業を続ける。** 通知は「終わった」としか言わない。
中身を読まずに次へ進まない。

終了コードが 0 でも、中身が期待どおりとは限らない。何を確かめたくて起動した
のかに戻って、その一次証拠を出力から取る。

## ターンを終える前に

未了の処理が残っているなら、**それを起こす仕組みが armed になっていることを
確かめてから終える。** 背景の Bash、Monitor、`/loop` の `ScheduleWakeup` の
いずれか。何も armed でないまま終えると、結果は永久に見られない。

harness が追えない外部の処理（CI、リモートのキュー、他人が回すジョブ）は、
状態が変わる速さに合わせて起こす仕組みを別に置く。

## 報告のしかた

見ていない結果を語らない。まだ動いているなら「まだ動いている」と言う。
起動しただけで結果を推測して書くのは、嘘をつくのと同じ。
