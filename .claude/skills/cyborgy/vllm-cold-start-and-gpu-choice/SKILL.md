# vLLM のコールドスタートを潰す

推論サービスの「最初の1回が返らない」を直す。**遅延の最適化より先に、ここを見る。**
使う人が待たされて諦める時間は、1トークンあたりの数ミリ秒より桁が大きい。

## 先に測る。犯人を思い込まない

コールドスタートを縮める前に、**必ず内訳を秒単位で割る。** 直感はよく外れる。

実測例(L4、2B モデル、vLLM 0.13.0、fp8、Cloud Run)。合計 **117 秒**:

| 区間 | 秒 |
|---|---:|
| インスタンス起動 → HTTP が listen | 8.6 |
| サービスのコード読み込み(vLLM 到達前) | 29.4 |
| **vLLM の engine 構築** | **57.5** |
| 音声エンコーダ・話者埋め込み等の読み込み | 11.2 |

vLLM 57.5 秒の中身:

| 区間 | 秒 |
|---|---:|
| `from vllm import LLM` の import | 14.0 |
| 設定の構築 | 16.7 |
| engine の spawn / 再 import / IPC | 10.2 |
| engine 初期化・model runner 準備 | 6.9 |
| **重みの読み込み(safetensors + fp8)** | **3.8** |
| ダミーのプロファイル実行 | 3.3 |
| KV cache 確保 | 1.3 |
| **CUDA graph capture** | **0.4** |

**重みは 3.8 秒、CUDA graph は 0.4 秒しかない。** 大半は **Python の import と
プロセス起動**である。モデルでも GPU でもない。

## 追ってはいけない道

- **CUDA graph を外す** … capture は 0.4 秒。起動は縮まず、定常時の速度だけ失う。
  **CUDA graph はディスクに保存できない**(生きた CUDA コンテキストと
  メモリアドレスに紐づく)ので、「保存して使い回す」もできない。
- **推論エンジンをやめて素の transformers に戻す** … 起動は縮むが生成が数倍遅くなる。
  実測: 同じ重み・同じ29トークンで、transformers BF16 は vLLM FP8 の
  **3.7〜5.3 倍遅い**。起動の数十秒と引き換えに、**毎回**の生成を犠牲にする取引になる。
  頻度が違う。
- **重みを小さくする / 読み込みを速くする** … 3.8 秒しかない。

## 効く道: プロセスの状態ごとスナップショット

import 済み・初期化済みの状態を丸ごと保存して、次回そこから復元する。
**import とプロセス起動を消せる唯一の方法**である。

Modal の GPU Memory Snapshot での実測(L40S、同じモデル):

| | 秒 |
|---|---:|
| スナップショットなし(engine 構築) | 41.97 |
| 復元後の vLLM wake(engine 内部) | **0.24** |
| **クライアント要求 → 生成可能(コンテナ復元込み)** | **8.08** |

生成結果は復元後も token ID 列まで一致し、速度の劣化もなかった。

### 書き方に条件がある

```
enable_memory_snapshot=True
experimental_options={"enable_gpu_snapshot": True}
```

**`LLM` オブジェクトをクラスに直接持つ書き方では、スナップショット作成に失敗する。**
vLLM を server subprocess として起こし、**warmup 後に sleep level 1 で重みを CPU へ
退避し、KV cache を破棄してから**スナップショットを取る形にする。

alpha 機能なので、**採用前に現在の仕様と制約を公式ドキュメントで確認すること。**
ここに書いた手順が古くなっている可能性がある。

## GPU を選ぶ

デコードは**重みを読むメモリ帯域**で律速する。prefill は短い(実測: 音声4.5秒ぶんで
12 ms)。**帯域の大きい GPU を選ぶのが最も効く。**

同一モデル・同一プロンプト・29トークンでの実測:

| GPU | 量子化 | ms/token | engine 構築 |
|---|---|---:|---:|
| L4 | fp8 | 12.6 | 63.4 s |
| A10 | bf16 | 10.5 | 38.9 s |
| L40S | fp8 | **5.4** | 33.1 s |

**「帯域 × 読むバイト数」からの予測は外れることがある。** A10 は fp8 が使えず
重みが倍になるので L4 とトントンのはずだったが、実際は 17% 速かった。
**予測ではなく実測で決めること。**

fp8 が使えるのは Ada 世代以降。**安い T4 は fp8 が無く重みが倍になるので、
帯域が同等でも遅くなる。**

## 同時実行は「ほぼタダ」だが、設定が要る

デコードで読む重みは、同時に何件流れていても1つ。**バッチが増えても
1件あたりの時間はほとんど増えない。** ただし CUDA graph の capture サイズが
足りないと、重なった瞬間に graph が使えず eager に落ちる。

L40S、50 ms 差で2件目を投入した実測:

| capture サイズ | 1件目 | 2件目 |
|---|---:|---:|
| `[1]` | **+105%** | **+102%** |
| `[1,2,4]` | +11.5% | **+1.1%** |

**`[1]` のままだと同時実行が壊れる。** capture は1サイズ 0.4 秒程度なので、
**複数を捌く予定があるなら最初から広げておく。**

なお、これを活かすには**エンジン側だけでなく、サービス側の直列化も外す**必要がある。
同期の `LLM` API とグローバルロックで囲っていると、2人目は1人目の完了を丸ごと待つ。
連続バッチングを使うなら `AsyncLLM` / `AsyncLLMEngine`、または vLLM のサーバーを立てる。

## 起動をさらに詰める小技

- **`VLLM_ENABLE_V1_MULTIPROCESSING=0`** … 同期 API + ロックで直列化している構成なら
  engine を別プロセスにする意味がない。spawn の 10 秒前後が消える。
- **`max_num_batched_tokens` と `max_num_seqs` を実態に合わせる** …
  既定の 8192 / 256 でダミー推論を走らせている。batch 1 しか来ないなら無駄。

## 検収

コールドスタートを縮めたと言う前に、次を確認する。

- **復元後の出力が、復元前と一致するか。** token ID 列まで見る。
- **復元後の生成速度が落ちていないか。**
- **利用者が実際に待つ時間**で測ったか。engine 内部の秒数ではない。
  リクエストログの latency から、インスタンス起動を伴った回を拾って測る。
- **サービス全体か、エンジン単体か**を混ぜていないか。
  エンジンの 42 秒を直しても、その前後の import が 40 秒あれば体感は変わらない。
