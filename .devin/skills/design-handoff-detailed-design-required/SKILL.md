# 実装を依頼する前に詳細設計を終える

実装を他者（他のエージェント、他のモデル、他の担当者）に依頼する場合、**依頼者が詳細設計まで行う。**

## 到達すべき状態

実装者に残ってよいのは、次のような**細部の解決だけ**である。

- コンパイルエラー・型エラーの解消
- ライブラリのバージョン不整合、API シグネチャの差異の吸収
- import、リンタ、フォーマッタへの適合
- 環境固有の差異（パス、OS、シェル）の吸収

**設計判断を実装者に残さない。**「どう分けるか」「どの型にするか」「どの順で行うか」を実装者が決めなければ進めない状態で渡したなら、それは詳細設計が終わっていない。

実装者が判断すれば、その判断は誰にも検証されない。依頼者は結果しか見ないので、設計と違う実装が入っても気づけない。詳細設計は実装者への親切ではなく、**検証可能性の要件**である。

## 詳細設計に記載すること

次を含む。これらに限らない。

- **層** — 追加・変更するコードが `platform` / `external` / `domain` / `application`
  のどれに属するか。層の定義はリポジトリのスキルに従う（次節）
- **クラス設計** — 何をクラスにするか、何を所有するか、生存期間、他との参照関係
- **メソッド設計** — シグネチャ、引数と返り値、呼び出し順序、失敗時の返り方
- **アルゴリズム** — 手順、判定条件、境界条件、計算量が問題になるならその見積もり
- **データの受け渡し** — どの値がどこで生成され、どこまで生き、誰が書き換えるか
- **実装時に考慮しなければならない重要事項**（後述）

## 層を決めるのは設計者の仕事

コードは、**そのコードが何を知ってよいか**で層に分ける。

| 層 | 知ってよい範囲 |
|---|---|
| `platform` | OS とランタイムの差異だけ |
| `external` | 外部のソフトウェア・サービスの仕様 |
| `domain` | 自プロダクトが保証する概念 |
| `application` | すべて。外部ごとの分岐はここにしか置かない |

`external` と `domain` は兄弟であり、互いを参照しない。**ドメインが
外部の差異を知らないことが、外部を追加しても保証が変わらないことを成立させる。**

層の正確な定義と判定方法はリポジトリのスキルにある。
**仕様には「どの層に置くか」を明記し、実装者に選ばせない。**
既存コードを変更する依頼なら、その範囲を層に適合させる作業も仕様に含める。
適合させる影響範囲が目的に対して広すぎると判断した場合は、**その判断と理由を仕様に書く**。

## 「重要事項」は壊れ方まで書く

実装者が知らずに壊しうるものを列挙し、**それを破ったとき何が起きるか**まで書く。「注意すること」では足りない。守る理由が分からない制約は守られない。

- 同一オブジェクトでなければ成立しないもの（コピーを渡すと壊れるもの）
- 排他制御 — ロックの種類、再入可否、取得順序、分割してはいけない臨界区間
- 実行順序の制約と、その根拠
- 副作用が既に発生した後の分岐（やり直せない地点）
- スレッド・非同期の境界、どのスレッドから触られるか
- 消してはいけない一見冗長な処理と、その理由
- **直したくなるが直してはいけないもの** — 見つけたら直さず報告する、と明示する

最後の項目は特に落としやすい。実装者は良かれと思って重複を統合し、デッドコードを消し、例外の範囲を絞る。それらは単体では改善でも、**「移動しただけ」という検証条件を壊す。**

## 検証条件も依頼者が決める

「何をもって完了とするか」を依頼時に示す。実装者に決めさせない。

- 実行するコマンドと、期待される出力
- 変更してはいけないファイル
- 目視で確認して報告させる項目

## 参照の鮮度を保つ

設計に行番号・シンボル位置・SHA を書いたなら、**渡す直前にその参照が現在のコードを指しているか確認する。** 別の作業でコードが動いていれば、行番号は静かにずれる。ずれた参照を渡すと、実装者は違う場所を書き換える。

## 渡す前の自己点検

1 つでも「実装者が決めることになる」なら、まだ渡さない。

1. 層は決まっているか
2. クラスとメソッドの境界は決まっているか
3. 単位をまたぐ値と、その所有者は決まっているか
4. 壊れうる箇所は、壊れ方まで書いてあるか
5. 完了条件は測定可能か
6. 参照している行番号・シンボルは今のコードに一致するか
