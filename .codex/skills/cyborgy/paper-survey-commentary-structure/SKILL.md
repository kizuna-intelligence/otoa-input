# 論文・サーベイ解説の構成規律

適用対象: 論文1本の解説、複数論文の統合解説、サーベイ結果の解説文書。

## 前提

- 原文(PDF 全文)を精読してから書く。abstract や他者の要約だけで書かない。取得・変換などの機械作業は委譲してよいが、精読と執筆は解説の書き手自身が行う。
- 既存の解説・プロジェクト文脈(glossary、検討ログ)を確認し、既存解説を置き換えるのか、何を追加するのか(基礎・本質・なぜ)を冒頭に明示する。
- 数値・固有名詞は原文で確認した値のみ書く。著者名は別経路で確認できない限り書かず、タイトル+arXiv ID にとどめる。

## 文書構造(この順で書く)

1. **ヘッダ**: 日付・精読範囲・目的・対象論文(ID・会議)・既存解説との関係。
2. **用語リスト**: japanese-glossary-for-explanations の規律に従う(プロジェクト用語表準拠、新語は★印を付けて用語表にも追記)。
3. **第I部 基礎理論・定式化**: 対象論文を理解するのに必要な定式化・基礎概念を特定し、解説の前半に独立部として置く。
   - 各節は「定義 → 式 → それが後の論文理解のどこに効くか」の順で書く。重要な式は表示数式で教科書品質にする。
   - 複数論文を扱うときは共通基礎を1つの部に統合し、重複解説を禁止する。論文固有の部品(例: 特殊なモデル構造)も基礎部に置き、本体からは参照する。
4. **各論文につき次の4節**(サーベイでは論文群ごとにまとめてよいが、(b)(c) は個々の論文について落とさない):
   - (a) **論文が主張する貢献**: 彼らの言い分を短く正確に。
   - (b) **本質的に解決した課題(自分の読み)**: 主張の芯を剥いだ一段抽象の課題を特定し、それが本質である証拠(消去実験・数値・構造的事実)を添える。「我々の読み」であることを明示する。
   - (c) **解決されなかった課題と、なぜ解決されなかったか**: 各項目に難しさの機構(数学的制約・問題設定ごと回避・測定のトレードオフ・計算規模など)まで書く。「解こうとして解けなかった」のか「そもそも問うていない」のかを区別する。
   - (d) **解決のアプローチ**: 部品の要約。鍵になる式だけ本体に置き、残りは基礎部を参照する。
5. **横断部**(複数論文・サーベイのとき必須): 軸を揃えた対比表+統合の読み。どの空白が残るか、(プロジェクト文脈があれば)自分たちの位置と輸入できる資産をここに書く。

## サーベイ解説への拡張

- 論文数が多いときは群(系譜・レーン)単位で4節構造を適用し、代表論文だけ個別に掘る。
- 「全員が解いていない課題は何か・なぜ全員にとって難しいのか」をサーベイの結論として明示する。空白の特定がサーベイ解説の本体である。

## 組版・印刷の罠

- 数式は math-typeset の規約に従う(表示数式・数式内に日本語禁止・mathtext 方言の制限)。
- **数式ブロックを含む列挙に markdown の番号付きリストを使わない**(数式で分断され番号が 1 に振り直される)。太字ラベルの段落 `**(1) 名前**: …` を使う。
- ビルド → 検版画像を全頁目視 → 修正 → 再検版 → 印刷(kizuna-printer-defaults)。検版前に印刷しない。

## 完成条件(自己検証)

- 上記構造がすべて存在する。数値が原文と一致する。用語が用語表と一致する。検版に合格している。
- 最後に自問する: (b) の「本質」と (c) の「なぜ」が、論文の自己申告(limitations 節)の言い換えになっていないか。なっていたら書き直す。
